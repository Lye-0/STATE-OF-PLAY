# パーツを既存プロジェクトへ導入する

v3.1.0では、パーツの配布構成と、STATE OF PLAY自体の開発構成を分けています。
このページの構成選択は**サイト内のパーツZIP**についての説明です。リポジトリ全体のZIPは元の階層を完全に保持します。

## 1. 形式と配置を選ぶ

詳細画面上部で、実装形式（TSX / JSX / TS / JS）と配置を選びます。

| 配置 | 用途 |
| --- | --- |
| 導入向け（初期値） | パーツ本体と専用補助処理を1フォルダーにまとめ、既存アプリへ持ち込む |
| 元の構成 | `src/parts/...`、`src/shared/...`を維持し、元実装と比較・参照する |

選択内容を変更すると、ファイルツリー、読み込みパス、コード、使い方、プロンプト、ZIPを同じデータから更新します。
選択していたファイルは元ソースの識別子で引き継ぎます。例えばTSXからJSXへ切り替えても、対応するコンポーネントを選択したままになります。
動作プレビューの状態は、配布構成の変更だけではリセットしません。
設定保存が利用できるブラウザーでは最後に選んだ配置・形式を記憶します。

## 2. 取り込むのは本体フォルダー

ChromeのReact TSX版の例です。

```text
chrome-tsx-portable/
├─ chrome-toggle/            # アプリへ持ち込む本体
│  ├─ ChromeToggle.tsx       # 公開する入口
│  ├─ styles.css
│  ├─ markup.html            # レイヤー構造の参照用
│  └─ internal/              # このパーツが必要とする専用補助処理
│     ├─ use-toggle.ts
│     ├─ toggle-controller.ts
│     ├─ motion.ts
│     └─ renderer.ts
├─ examples/                 # 使い方の例。既存のApp/mainへ上書きしない
│  └─ Example.tsx
├─ preview/                  # 独立確認用デモ。アプリへ取り込まない
├─ README.md
├─ PROMPT.md
└─ INTEGRATION.json
```

ZIPの実際のファイル一覧は選択したパーツ・形式によって変わります。上記は配置の例です。
`chrome-toggle/`を、既存の規約に合わせた場所へフォルダーごと配置します。
例えば`src/components/ui/`、`src/features/settings/components/`、モノレポ内の対象アプリのコンポーネント置き場です。
これらは例であり、特定の`src/`や`@/`エイリアスを要求しません。

本体の内部を分割・改名しなければ、内部の相対参照は維持されます。
外側から使うimportは、**実際に置いた場所に合わせて**記述してください。
使用例を別の場所へ移す場合は、使用例自身のimportも変更します。

React版は既存のReact環境が必要です。通常TS版はTypeScriptの変換が必要です。
通常JS版はネイティブES ModulesなのでローカルHTTPサーバーから実行します。
元実装に含まれる`'use client'`やCSS importは維持しますが、SSR・CSSの規則は導入先のフレームワークでも確認してください。

## 3. 元の構成を使う場合

元の構成では、パーツと必要な共有処理の`src/...`階層を保存します。
複数パーツを、既存プロジェクトの同じ`src/shared/`へ無条件に上書きすることは推奨しません。
まず各パーツ専用の親フォルダーへ`src/`ごと配置するか、内容とバージョンを確認して再配置してください。
再配置する場合はimport/export、CSSや素材の参照、使用例を同時に更新します。

## 4. 複数パーツ・同じパーツの更新

導入向けではパーツごとに内部処理が分かれます。同名の`motion.ts`が別のパーツにあっても、名前だけで共通化しません。
同一のコード・API・バージョンであることを確認したうえで共通化を検討します。
これは配布時の独立性のための複製であり、STATE OF PLAYの開発用ソースでは引き続き共有処理を1か所で管理します。

既存に同じパーツがある場合は、古いものを自動削除しません。`INTEGRATION.json`のID・バージョン・元パスを使って変更内容とローカル修正を比較します。
このファイルは配置の記録であって、インストーラーやファイル上書き指示ではありません。

## 5. AI用プロンプト

「コード込み」と「再現仕様のみ」の2形式です。配置と実装形式の選択を両方へ反映します。
「コード込み」をコピーすると、画面で確認した配置・ソースに、対象アプリを調査してから組み込むための共通ルールを添えます。

AIには、AGENTS.md等の指示、対象アプリ、package.json、既存ロック、TypeScript/ビルド設定、CSS規則を確認させます。
プロジェクトを参照できない場合は必要な構成だけを質問し、秘密情報や.envの提示を求めない内容です。
外観と動作を保ちながら配置・読み込み先を適応させ、既存ファイルやApp/main、共通処理を無条件に上書きさせません。

サイト自体が利用者のプロジェクトを読み取る仕組みではありません。
文章だけでの再実装やAIの動作について、完全一致や無事故を保証するものではありません。元ソースとの差分と実際の動作を確認してください。

## 6. 保存形式は配置と別

ZIP画面には、選択済みの配置・入口と、最終的なZIP内のツリーを表示します。
その下で「通常ソース」と「テキスト保管用」を選びます。配置を変える選択とは別です。
テキスト保管用はファイル名末尾に`.txt`を付けるもので、階層は同じです。元の拡張子へ戻すまで実行用には使いません。
`INTEGRATION.json`内の配置パスは元へ復元したソースのパスを表します。
Windowsの入手元判定や保護機能を変更・回避するものではありません。

個別の「ファイルを保存」はブラウザーの通常ダウンロードで1ファイルだけを取得します。
内部の相対パスを記録したまま複数のファイルを持ち込む場合はZIPを使ってください。
